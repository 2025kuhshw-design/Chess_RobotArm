# 보고서용 정리 — 설계(PPT) 대비 실제 구현 변경점 & 소감

발표 PPT의 설계안과 실제 구현 결과를 대조한 기록.
"계획대로 되지 않은 부분"이야말로 공학 프로젝트의 핵심 내용이므로 정직하게 남긴다.

---

## 1. 계획대로 구현된 것

| 항목 | 설계 | 결과 |
|---|---|---|
| 잡는 방식 | 흡착식 | ✅ 진공 펌프 + 솔레노이드 밸브 |
| 관절·모터 | 관절 4개 · 모터 3개 (MG996R) | ✅ 동일 |
| 체스판 | 23.3 × 23.3 cm, 원형 평면 기물 | ✅ 한 칸 2.91 cm, 기물 높이 7 mm |
| 카메라 인식 | OpenCV 탑뷰 변환 → 8×8 분할 → 기물 분류 | ✅ 구현 |
| 수 감지 | 이전/현재 프레임 비교로 변화 칸 추출 | ✅ 구현 |
| 역기구학 | 목표 좌표 → 관절 각도 계산 | ✅ 구현 |
| 움직임 강화학습 | PyBullet 1·2단계 학습 | ✅ 600만 스텝 완료 |

## 2. 설계와 달라진 것

### ① 체스 두뇌: Lc0 → **Stockfish**
- **설계**: Lc0(Leela Chess Zero)를 자가 대국으로 학습, 구조적 프루닝·양자화로 경량화
- **실제**: Stockfish 엔진을 그대로 사용 (`utils/chess_utils.py`)
- **이유**: 프로젝트의 실제 난관이 체스 실력이 아니라 **물리 제어**에 있었다.
  체스 두뇌는 이미 검증된 엔진을 쓰고, 남은 시간을 로봇팔 정확도에 집중하는 편이
  전체 완성도를 높이는 선택이었다.

### ② 응답 시간: 1.7초 → **한 수 20~30초**
- **설계**: 전체 파이프라인 1.7초 (서보 실행 1,000 ms)
- **실제**: 안전을 위해 **의도적으로 느리게** 만듦
- **이유**: 목표 각도로 한 번에 명령하면 서보가 최고 속도로 움직이는데,
  이때 걸린 충격으로 **서보 내부 기어가 파손되는 사고**가 있었다.
  이후 목표까지 2°씩 나눠 보내는 **램프(ramp) 이동**과, 팔의 잔류 진동이
  가라앉기를 기다리는 **정착 대기(0.4초)**를 넣었다.
  → 속도를 포기하고 안전성과 정확도를 얻은 설계 변경.

### ③ 통신 프로토콜: 최소 바이너리 → **ASCII 문자열**
- **설계**: CMD 1바이트 + XY 2바이트 경량 패킷
- **실제**: `"A{각도1},{각도2},{각도3},{흡착}\n"` 형식
- **이유**: 디버깅 중 시리얼 모니터로 직접 명령을 넣어 확인해야 할 일이 많았다.
  사람이 읽고 쓸 수 있는 형식이 개발 속도에 훨씬 유리했고,
  통신량이 병목이 아니어서 경량화 이득이 없었다.

### ④ 하드웨어 제어: 아두이노 직결 → **PCA9685 드라이버 경유**
- **설계**: 아두이노 UNO가 서보를 직접 PWM 제어
- **실제**: PCA9685 16채널 PWM 드라이버를 추가하고 아두이노는 I2C 신호만 담당
- **이유**: 서보 3개 + 펌프 + 밸브 5개를 아두이노 핀으로 직접 구동하기엔
  전류가 부족했다. 전원 계통을 분리해야 했다.

## 3. 계획에는 있었으나 완료하지 못한 것

| 항목 | 상태 | 사유 |
|---|---|---|
| Sim-to-Real **3단계**(실기 fine-tune) | 미완 | 기구학 모델 수정으로 기존 학습 모델을 쓸 수 없게 됨(아래 참고) |
| 카메라 **3프레임 다수결** 판정 | 미구현 | 단일 프레임으로도 인식이 안정적이어서 우선순위에서 밀림 |
| 카메라 **조명 정규화** | 미구현 | 조명 위치 조정·반사 억제 등 물리적 대응으로 대체 |
| **FEN 문자열** 출력 | 미구현 | 변화 칸(from/to) 좌표를 직접 넘기는 방식으로 충분했음 |
| 라그랑주 방정식 **궤적 최적화** | 부분 | 토크 계산·한계 검증에는 사용하나, 에너지 최소 경로 계산까지는 미적용 |
| Lc0 프루닝·양자화 | 미실시 | 엔진을 Stockfish로 변경하면서 불필요해짐 |

## 4. 계획에 없었으나 새로 필요했던 것

실제로 만들어 보니 **설계안에 존재하지 않던 문제들**이 나타났다.

### ① 역기구학 모델에 빠져 있던 물리량 2개
- **어깨 관절 높이(`SHOULDER_HEIGHT`)**: 기존 코드는 어깨 관절이 체스판 표면과
  같은 높이라고 암묵적으로 가정하고 있었다. 실제로는 **8.9 cm 위**에 있었다.
- **팔꿈치 자세(`ELBOW_SIGN`)**: 2링크 역기구학은 같은 목표점에 두 가지 해
  (elbow-up / elbow-down)가 존재하는데, 코드는 한쪽만 사용하고 있었다.
  실제 팔의 서보 가동 범위에 맞는 해는 반대쪽이었다.

→ 이 둘을 넣기 전까지는 **모든 칸이 서보 가동 범위를 벗어나** 팔이 체스판에
  닿을 수조차 없었다. 실물을 만들기 전에는 드러나지 않는 종류의 오류였다.

### ② 좌표계 오류 두 가지
- **거울상(handedness) 오류**: 카메라 격자 → 로봇 좌표 변환이 좌우가 뒤집힌
  좌표계였다. 방향만 맞춰도 실제로는 반대편 칸을 짚게 되는 상태였다.
- **랭크·파일 축 반전**: 랭크(1~8)가 좌우 방향에 배정되어 있어, 사람 앞 두 줄이
  랭크 1·2가 아니라 g·h 파일이 되었다. 그대로 두면 사람이 둔 수를 체스 엔진이
  **전부 불법 이동으로 판정**하여 게임이 진행되지 않는다.

### ③ 안전 장치 일체
설계안에는 없었지만, 기어 파손과 드라이버 소손을 겪은 뒤 필수가 되었다.
- 목표까지 나눠 이동하는 **램프 제어**
- 전원 인가 직후의 **기동 절차** (팔이 처진 상태에서 갑자기 튀는 것 방지)
- 관절별 **소프트 각도 제한**
- **펌웨어 버전 자동 확인** (아두이노 재업로드 누락 감지)
- 서보 범위를 벗어나면 조용히 넘어가지 않고 **명시적으로 실패**시키기

### ④ 실측 기반 위치 보정
- 강화학습만으로는 실제 오차가 줄지 않는다는 것을 확인한 뒤,
  **체스판 격자를 눈금 삼아 오차를 직접 재고** 최소제곱으로 보정식을 구하는
  방식을 추가했다(`hardware/calibrate_board.py`).

### ⑤ 그 외
- 잡은 기물을 놓는 **캡처 구역** (기존 방식은 팔 길이를 초과해 오류 발생)
- 칸별 **적응형 리프트 높이** (먼 칸에서 도달 불가가 되는 문제 해결)

## 5. 강화학습 모델에 대한 정직한 기록

발표 시점에는 "600만 스텝 학습 완료, 목표 초과 달성"으로 보고했다. 이는 사실이다.
그러나 이후 **역기구학 모델을 수정하면서 그 모델을 사용할 수 없게 되었다.**

- 학습 당시 관절각 범위: q2 −31°~+7°, q3 +19°~+119°
- 수정 후 관절각 범위: q2 +11°~+68°, q3 −130°~−24°
- **겹치는 구간이 0°** — 모델이 한 번도 본 적 없는 입력이므로,
  출력되는 보정값은 근거 없는 외삽이다.

또한 더 근본적인 문제를 확인했다.
**시뮬레이터에서 학습한 보정은 "해석적 역기구학 ↔ 시뮬레이터 동역학"의 차이를
학습한 것이지, 실제 로봇의 오차를 학습한 것이 아니다.** 실물을 한 번도 보지 않은
정책이 실물의 오차를 줄일 수는 없다.

→ 실제 정확도 개선은 **실측 기반 보정**으로 달성했고, 강화학습은 시뮬레이션
   성능 지표로서의 의미를 갖는다. 두 방법을 비교한 것 자체가 이 프로젝트에서
   얻은 가장 큰 배움이다.

## 6. 소감 (초안 — 자신의 표현으로 다듬을 것)

2학년 때 강화학습으로 체스 AI를 만들었을 때는 CMD 창에 승률이 올라가는 것만 봐도
충분히 성취감이 있었다. 그런데 그 AI는 화면 안에만 있었다. 이번에는 그것을 현실로
꺼내오고 싶었고, 그래서 로봇팔을 붙이기로 했다.

**시뮬레이터에서 완벽했던 것이 현실에서는 시작조차 못 했다.**
600만 스텝을 학습시켜 목표치를 초과 달성한 모델이 있었지만, 실제 팔을 조립하고
나서야 역기구학 코드에 두 가지가 빠져 있다는 걸 알았다. 어깨 관절이 체스판보다
8.9 cm 위에 있다는 사실과, 우리 팔의 팔꿈치가 코드가 가정한 방향과 반대로
꺾인다는 사실이었다. 이 둘을 넣기 전까지 로봇팔은 **체스판에 닿을 수조차 없었다.**
숫자로는 몇 줄 되지 않는 값이지만, 그 값이 없으면 아무리 잘 학습된 모델도
소용이 없었다. 시뮬레이션이 현실을 얼마나 단순화하고 있었는지를 그때 처음
체감했다.

**"강화학습으로 보정한다"는 말의 의미도 다시 생각하게 되었다.**
기구학을 고치고 나니 기존 학습 모델을 쓸 수 없게 되었다. 학습 당시와 지금의
관절각 범위가 전혀 겹치지 않아서, 모델 입장에서는 한 번도 본 적 없는 상황이었기
때문이다. 재학습을 준비하면서 더 근본적인 사실을 깨달았다. 시뮬레이터 안에서
학습한 보정은 시뮬레이터와 수식의 차이를 배운 것이지, **우리 로봇의 실제 오차를
배운 것이 아니었다.** 실물을 한 번도 본 적 없는 정책이 실물의 오차를 줄일 수는
없었다. 결국 정확도를 실제로 올린 것은, 체스판에 인쇄된 격자를 눈금 삼아 로봇이
실제로 어디를 짚는지 직접 재고 그 오차를 수식으로 보정한 방법이었다. 화려한
기법보다 **직접 재는 것**이 앞선다는 것을 배웠다.

**실패도 많았다.** 서보에 한 번에 큰 각도를 명령했다가 내부 기어가 갈리는 소리를
들었고, 흡착 펌프의 순간 전류가 모터 드라이버를 통과하게 배선했다가 드라이버를
태웠다. 카메라 좌표계가 거울상으로 뒤집혀 있어 로봇이 정반대 칸을 짚기도 했고,
랭크와 파일 축이 바뀌어 있어 사람이 둔 수를 엔진이 전부 불법이라고 판정한 적도
있었다. 이런 문제들은 설계안 어디에도 없었다. **만들어 보기 전에는 존재조차 알 수
없는 문제들이었다.** 그래서 지금 우리 코드에는 설계 단계에 없던 것들이 여럿
들어가 있다. 목표 각도로 한 번에 가지 않고 조금씩 나눠 보내는 제어, 전원을 켤 때
팔이 갑자기 튀지 않게 하는 기동 절차, 아두이노에 최신 코드가 올라가 있는지
자동으로 확인하는 장치 같은 것들이다. 전부 무언가를 망가뜨린 뒤에 생긴 것이다.

**설계는 시작점이지 정답이 아니었다.**
발표 때 우리는 응답 시간을 1.7초로 잡았지만, 실제로는 한 수에 20~30초가 걸린다.
빠르게 움직이면 기어가 상하고 팔이 흔들려 기물을 정확히 집지 못했기 때문에,
속도를 포기하고 안전성과 정확도를 택했다. 체스 두뇌도 직접 학습시킨 모델 대신
검증된 엔진으로 바꾸었다. 우리 프로젝트의 진짜 어려움이 체스 실력이 아니라
**물리 세계를 제어하는 일**에 있다는 것을 알게 되었기 때문이다. 계획을 지키지
못한 것이 아니라, 실제로 부딪히며 더 나은 선택으로 바꿔 나간 과정이라고 생각한다.

「피지컬 AI 패권전쟁」에서 읽은 "누가 현실의 물리적 변수를 더 잘 통제하는가"라는
문장이, 프로젝트를 시작할 때는 멋있는 말로만 들렸다. 지금은 그 문장이 어깨 높이
8.9 cm, 기물 두께 7 mm, 흡착컵을 4 mm 더 눌러야 진공이 걸린다는 것 같은,
아주 구체적인 숫자들의 이야기라는 것을 안다. **현실은 코드보다 훨씬 많은 변수를
가지고 있었고, 그 변수를 하나씩 재고 맞춰 나가는 것이 피지컬 AI였다.**

아직 끝나지 않았다. 남은 것은 팔의 흔들림을 잡고, 실측 보정을 마치고, 사람과
한 판을 끝까지 두는 것이다. 처음 계획한 모습과 많이 달라졌지만, 그 차이만큼
실제로 배웠다고 생각한다.
